## 모임 소개
외부 API 연계와 실전 모니터링
"결제는 됐다는데, 우리 DB엔 없어요."
"PG사가 잠깐 흔들렸을 뿐인데 전체 서비스가 멈췄어요."
"커넥션풀이 부족하다는데, 얼마로 늘려야 하는지는 아무도 모릅니다."
외부 API 연동은 처음 붙일 때보다 장애가 났을 때 진짜 모습이 드러납니다.
이 워크숍은 결제·주문 같이 돈이 오가는 경계에서 실제로 마주치는 문제들을 — 멱등성, 서킷브레이커, 정합성, 커넥션풀 산정, 벌크헤드, 이중화 — 4주에 걸쳐 코드와 실험으로 직접 다뤄봅니다.

## 이번 모임에서 얻어가는것

운영 가능한 외부 API 연동 코드

운영 가능한 외부 API 연동 코드 교과서적 예제가 아니라, 타임아웃/재시도/멱등성/서킷이 동시에 동작하는 실제 구조를 직접 짭니다.

풀 사이즈를 계산으로 설명하는 능력

"감으로 잡았어요"에서 벗어나, TPS와 latency를 기반으로 한 산정 근거를 동료/PM/리더에게 설명할 수 있게 됩니다.

장애 시나리오 기반 사고 체계

"이 의존성이 죽으면 우리 시스템은 어디까지 죽는가"를 그림으로 그리고 코드로 막을 수 있게 됩니다.

1
외부 API는 언제든 실패한다 — 같은 요청을 두 번 보내도 안전하게 만드는 법

세션
멱등 처리, Circuit Breaker, Fallback

7. 4.
10:00~12:00
Idempotency Key를 어디서(클라이언트/게이트웨이/도메인) 생성하고 어디까지 전파해야 하는지 설계 의사결정을 내릴 수 있다.
DB unique constraint, Redis SETNX, Optimistic Lock 중 도메인 특성에 맞는 멱등 처리 방식을 선택하고 그 근거를 설명할 수 있다.
Resilience4j의 Circuit Breaker 상태 전이를 로그로 관찰하고, sliding window size와 failure rate threshold를 시나리오에 맞게 튜닝할 수 있다.
Fallback 응답이 조용한 실패 가 되지 않도록, 알람/메트릭과 함께 설계할 수 있다.

2
결제는 성공했는데 우리 DB는 모를 때 — 경계를 넘는 트랜잭션의 정합성

6. 27. ~ 6. 27.

세션
에러 처리, 정합성 회복

7. 11.
10:00~12:00
외부 API 호출과 로컬 트랜잭션의 경계를 어떻게 그을지(트랜잭션 안 vs 밖) 결정하고, 그 선택의 트레이드오프를 설명할 수 있다.
PG사 timeout처럼 응답을 모르는 상태(unknown state) 에서 결제 상태를 조회·동기화하는 Reconciliation 잡을 직접 구현할 수 있다.
예외를 재시도 가능 / 재시도 불가능 / 비즈니스 / 시스템의 네 축으로 분류하고, 각각에 대해 다른 대응 전략을 코드로 표현할 수 있다.
보상 트랜잭션(Compensating Transaction)이 필요한 시나리오와 단순 롤백으로 충분한 시나리오를 구분할 수 있다.

Little's Law를 우리 시스템의 TPS와 평균 latency에 대입하여 필요 커넥션 수를 계산할 수 있다.
HikariCP의 핵심 파라미터의 의미와 잘못 설정했을 때의 증상을 매칭할 수 있다.

Bulkhead 패턴, 이중화

7. 25.
10:00~12:00
Bulkhead 패턴을 Semaphore 방식과 ThreadPool 방식으로 각각 구현하고, 두 방식의 격리 수준과 비용을 비교 설명할 수 있다.
외부 의존성 하나의 장애가 전체 스레드를 잠식하는 시나리오를 재현하고, Bulkhead로 막아내는 과정을 코드와 메트릭으로 보여줄 수 있다.
결제 PG 이중화 전략을 비용/정합성/운영 복잡도 관점에서 비교하여 의사결정할 수 있다.
1~3주차의 설계가 이중화 구조 위에서 어떻게 함께 동작해야 하는지를 전체 그림으로 설명할 수 있다.
